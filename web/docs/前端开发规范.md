# 前端开发实现规范（knowledge-web）

> 约定：本文档是 knowledge-web 前端代码的**实现规范**（怎么写代码、怎么组织工程），目标是可维护、可扩展、可协同。
> 与《实施手册》的"每阶段八步"和仓库级的提交/注释规范配套使用；后端接口契约不在本文范围（见 swagger-ui 与后端各阶段文档）。

## 1. 总则

1. **规则分级**（借鉴 Vue 官方风格指南的分级方式，全文统一用词）：
   - **【必须】**：规避错误的底线，违反即视为不合规代码，评审不通过；
   - **【应该】**：绝大多数场景下改善可读性与可维护性，违反需在评审中说明理由；
   - **【可以】**：多个同样好的选项里取一个为默认，保持全库一致即可。
2. **规范先行于习惯**：与本规范冲突的个人习惯一律让位；确有必要偏离的，先改本规范（评审通过后）再改代码。
3. **自动化优先**：凡是能用 ESLint / Prettier / 提交钩子机器化保证的条款，一律配置进工程强制执行，不靠人工记忆（见 §10）。
4. **界面纯中文**（已定）；代码与注释中的命名一律英文，见 §3。

## 2. 工程与目录规范

### 2.1 工程结构

工程目录为仓库根的 `web/`（包名 knowledge-web 保留 knowledge 前缀表示同属一个项目；顶层与后端 Maven 模块平级，字母序排在模块之后自然分区）。

```
web/
├── public/                 # 静态资源（原样拷贝进构建产物）
├── src/
│   ├── api/                # 接口层：按后端控制器分包，一控制器一文件（见 2.3）
│   ├── assets/             # 样式/图标/图片等经构建处理的资源
│   ├── components/         # 可复用组件（按领域再分目录）
│   ├── composables/        # 组合式逻辑复用（hooks）
│   ├── layouts/            # 布局组件
│   ├── router/             # 路由与守卫
│   ├── stores/             # 全局状态（待定方案）
│   ├── styles/             # 全局样式与设计变量（色板/间距/字号）
│   ├── types/              # 全局类型定义（与后端 DTO 对齐）
│   ├── utils/              # 纯工具函数（不依赖框架）
│   └── views/              # 页面：按业务模块分目录，一页面一目录
├── tests/                  # 与 src 同构的测试目录（待定方案）
├── .eslintrc / eslint.config.*
├── .prettierrc
└── package.json
```

### 2.2 目录与文件命名

1. 【必须】目录、普通文件（`.js/.ts/.css/.scss/.png` 等）一律 **kebab-case 小写中划线**；有复数语义的用复数（`utils`、`components`），缩写不用复数（`img`、`doc`）。
2. 【必须】`views/` 页面一页一目录，目录名 kebab-case 与路由 path 一致（`views/knowledge-base/` ↔ `/knowledge-base`）。
3. 【必须】`api/` 文件与后端控制器同名映射：`KnowledgeBaseController` → `api/knowledge-base.ts`。
4. 【必须】`components/` 内按领域分目录（`index/`、`retrieval/`、`common/`），目录名 kebab-case。

### 2.3 接口层（api/）职责收口

1. 【必须】所有 HTTP 调用只允许出现在 `api/` 目录内；页面/组件不得直接写请求。
2. 【必须】每个接口函数返回类型显式声明（后端 DTO 在 `types/` 的对应映射），不得写 `any`。
3. 【必须】请求参数与响应结构以 swagger-ui（`http://localhost:4388/swagger-ui.html`）为单一事实源，字段改名/改口径时先改后端、再同步 `types/`。
4. 【必须】后端雪花 Long 的 ID 字段一律按**字符串**类型处理（后端 VO 层 Long→String 序列化约定）。
5. 【必须】后端分页请求参数固定 `current`（1 起）/`size`；响应取 `records/total/size/current` 四字段，其余字段不得依赖。
6. 【必须】时间字段按后端 ISO 格式接收，展示统一经 `utils/` 时间工具格式化为 `yyyy-MM-dd HH:mm:ss`，禁止散落 `new Date(...).toLocaleString()`。

## 3. 命名规范（JS/TS）

1. 【必须】变量、函数、参数一律 **lowerCamelCase**；常量 `UPPER_SNAKE_CASE`；类与组件 **PascalCase**；CSS 类名 kebab-case。
2. 【必须】方法名必须是动词或动词+名词（`fetchPage`、`handleSubmit`）；增删改查统一用 `add / update / delete / get / detail` 五个词，不得另造（`create`、`remove`、`query` 等一律归一到这五个词）。
3. 【必须】禁止拼音、拼音英文混用、中文命名；禁止随意缩写（`condi`、`absCls` 之类），用完整英文单词。
4. 【必须】布尔变量以 `is/has/can/should` 开头（`isOnline`、`hasChildren`）；数组/集合变量用复数或 `List` 后缀；事件回调以 `on/handle` 开头（`onClick` 区分于 `handleSave`）。
5. 【必须】循环/条件/三目嵌套不超过 3 层，超出必须抽函数。
6. 【必须】`this` 需要暂存引用时只用 `self` 命名（历史兼容约定）。

## 4. JS/TS 代码风格

1. 【必须】缩进 2 空格；行尾分号必加；字符串一律单引号（模板字符串用反引号）。
2. 【必须】`const` 优先，仅需重新赋值时才用 `let`；禁止 `var`。
3. 【必须】`if/else/for/while/try/catch` 等代码块必须带大括号，即使只有一行。
4. 【必须】对象/数组用字面量（`{}`、`[]`），禁止 `new Object()`/`new Array()`。
5. 【必须】优先使用解构、箭头函数、模板字符串、可选链 `?.`、空值合并 `??`、`async/await`；禁止 `for...in` 遍历数组。
6. 【必须】判断 undefined 用 `typeof x === 'undefined'` 或 `x == null`，禁止直接 `x === undefined`。
7. 【必须】同一函数内不同逻辑/语义之间空一行分隔；禁止连续多个空行。
8. 【应该】函数只做一件事，超过 ~50 行拆解；参数超过 3 个改传对象。
9. 【应该】`console.log` 不得提交（调试用后即删；日志走统一封装）。

## 5. 组件规范（Vue 3）

1. 【必须】组件名始终多个单词（根组件除外），如 `TodoItem`。
2. 【必须】prop 定义尽量详细：camelCase 命名 + 类型 + `required`/`default` 二选一 + 用途注释；有枚举取值时加 `validator`。
3. 【必须】`v-for` 必须配 `key`（用稳定业务 ID，不用数组下标）。
4. 【必须】`v-if` 与 `v-for` 不得同时出现在同一元素：过滤场景抽计算属性，显隐场景 `v-if` 移到容器。
5. 【必须】组件样式必须 `scoped`（全局样式只允许进 `styles/`）。
6. 【必须】组件 `data` 必须是返回对象的函数。
7. 【必须】单文件组件顶级顺序固定：`<template>` → `<script>` → `<style>`。
8. 【必须】组件文件用 PascalCase 命名（`TodoItem.vue`）；模板中使用时也用 PascalCase 且自闭合（`<TodoItem />`）。
9. 【必须】基础组件用 `Base` 前缀（`BaseButton.vue`）；与父组件紧密耦合的子组件以父组件名作前缀（`TodoList` → `TodoListItem.vue`）。
10. 【必须】模板只放简单表达式，复杂逻辑一律进计算属性或方法。
11. 【必须】指令一律用缩写（`:`、`@`、`#`）。
12. 【应该】元素 attribute 较多时一行一个、属性换行；attribute 顺序统一（定义类属性 `class/id` → 绑定属性 `v-/:` → 事件 `@`）。
13. 【应该】`v-if`/`v-show` 选择：频繁切换用 `v-show`，运行期条件基本不变用 `v-if`。
14. 【应该】组件内选项顺序固定：`components → props → data → computed → watch → 生命周期钩子（按执行顺序）→ methods`；组合式 API 按 setup 内书写顺序保持一致。
15. 【可以】组件/实例选项之间空一行，提高扫描速度。

## 6. 样式规范

1. 【必须】类名 kebab-case、反映语义而非表象（`.important` 而非 `.red`）；禁止 ID 选择器与全局标签选择器。
2. 【必须】每个选择器及属性独占一行；`0` 值省略单位。
3. 【必须】优先使用缩写属性（`margin`、`padding`、`border`、`font`）。
4. 【必须】嵌套不超过 3 层；超过 4 层重新评估拆分。
5. 【必须】设计变量（色板/间距/字号/圆角）统一维护在 `styles/` 变量文件，页面/组件内禁止硬编码颜色值（个别业务色除外）。
6. 【应该】选择器尽量用直接子选择器（`>`）而非后代选择器。

## 7. 路由与状态

1. 【必须】路由一律懒加载（`component: () => import('@/views/...')`）。
2. 【必须】路由 path 用 kebab-case 且以 `/` 开头；路由 name 与页面组件名保持一致（PascalCase）。
3. 【必须】页面间传参用路由参数（query/params），禁止借全局状态传参（刷新即丢）。
4. 【必须】全局状态用 Pinia 管理，只放跨页面共享的数据（登录态等）；页面私有状态留在页面内，不得塞进 store。
5. 【必须】store 变更一律经 actions，页面内禁止直接改 store 数据。

## 8. 异步与错误处理

1. 【必须】异步统一 `async/await`，回调风格（then 链）不用于业务代码。
2. 【必须】请求层统一拦截：响应 `code !== 0` 统一提示 `msg` 并拒绝，页面只处理成功分支；`40101`（未认证）统一跳登录；`40500`（系统异常）统一兜底提示。错误码语义以《ErrorCode》为单一事实源。
3. 【必须】页面数据展示必须有"加载中/空数据/异常"三态，不得裸渲染。
4. 【必须】用户可见的写操作（提交/删除/发布）必须带二次确认与结果提示。
5. 【应该】组件卸载时取消未完成的请求/轮询，避免内存泄漏与竞态。

## 9. 注释规范

1. 【必须】注释只写"做什么"（职责与行为），不写"谁写的/为什么/从哪来/阶段 X"——与后端注释口径一致。
2. 【必须】组件 props、接口层函数、工具函数的公共入口必须有简短注释（职责一句话）。
3. 【应该】复杂算法的关键步骤与"容易踩坑"处补注释；注释与代码同步更新，不保留过期注释。

## 10. 工程化强制项

1. 【必须】ESLint + Prettier 全库统一配置，禁止个人改写规则绕过检查（确需放宽：先评审改规范，再改配置）。
2. 【必须】husky 双钩子门禁（日常开发零等待，提交/推送时自动把关）：
   - pre-commit（每次提交，秒级）：lint-staged 自动格式化与修复 + ls-lint 文件命名 + API 词表检查，不过不提交；
   - pre-push（每次推送，约 2 分钟，仅当本次推送涉及前端文件）：IDEA 无头检测（复用后端门禁脚本 `../tools/inspect-idea.ps1 -Scope web`）对本批推送的前端文件做 0 警告门禁，有警告阻断推送；
   - 手动预检命令保留：`pnpm lint`（秒级）/ `pnpm lint:idea`（全量）。
3. 【必须】提交信息沿用仓库 Conventional Commits：`feat(web)` / `fix(web)` / `docs(web)` / `chore(web)` / `refactor(web)`。
5. 【必须】Node/pnpm 版本在 `package.json`/`.npmrc` 钉住（当前环境 Node 24 / pnpm 11）。
6. 【必须】构建产物、`node_modules`、编辑器与系统文件进 `.gitignore`，禁止提交。
7. 【必须】新增依赖最小化：能用现有依赖解决的禁止引新库；引新库需在评审中说明理由。

## 11. 规则分级速查

| 等级     | 用词      | 违反后果                                     |
|----------|-----------|----------------------------------------------|
| 【必须】 | 必须/禁止 | 不合规，评审不通过（能机器化的一律机器拦截） |
| 【应该】 | 应该/不宜 | 需在评审中说明理由                           |
| 【可以】 | 可以      | 保持全库一致即可                             |
