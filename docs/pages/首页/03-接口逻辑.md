# 接口逻辑

两个接口都在 `KnowledgeHomeServiceImpl`，共用的两条实现原则：

1. **可见范围在服务端定**：最近提交只查当前登录用户（`kb_submit_log.user_id`），接口不接受"提交人"参数 —— 由前端传参决定查谁，等于没做隔离；
2. **批量反查、不逐行查库**：知识库名与文件类型都是先收集本页涉及的 ID，各查一次批量取回，再装配 VO —— 一次翻页最多 2 次附加查询，与页大小无关。

所有码值都走枚举（`StrategyType` / `FileFormat` / `KnowledgeBaseStatus`），服务里不持有字符串常量与映射表；策略版本的计数不手写条件，走 `KbPipelineStrategyVersionDbService.countEnabledByType`。

## `GET /home/summary`

| 数字                | 算法                                                                  |
|---------------------|-----------------------------------------------------------------------|
| 知识库总数 / 启用数 | `kb_knowledge_base` 计数，启用数按 `status = ACTIVE`                  |
| 四类策略版本数      | `kb_pipeline_strategy_version` 按 `type` + **`status = ACTIVE`** 计数 |
| 可用策略合计        | 上面四类相加（不让数据库再算一次全表）                                |
| 已建档文档数        | `kb_file_result` 计数（`countAll`）                                   |

两处口径：

- **策略版本只数启用中**：停用（`INACTIVE`）的版本仍留在表里可查，但不能被知识库绑定，界面上那一格叫「可用策略」，含停用会让文案名不副实；
- **文档数不是「提交数」**：文件校验不通过时（含文件不存在）**只写一条 `kb_submit_log(FAIL)`，不建 `kb_file_result`**（见 `FileSubmitServiceImpl` 的建档三写与失败分支）。所以 `kb_file_result` 行数 = 校验通过并已建档的文档数，`kb_submit_log` 行数才是全部提交记录 —— 资产带取前者（与知识库列表页的「文档数」同源），提交表取后者，两者天然不等。

## `GET /home/recent-submits`

数据源 `kb_submit_log`，按 `id` 倒序分页（新→旧），**PASS 与 FAIL 都在**，且**只查当前登录用户**（`user_id = 安全上下文里的用户 ID`）。

装配时补三样东西（前两样各一次批量查询）：

- `knowledgeBaseName`：按 `knowledge_base_id` 批量反查 `kb_knowledge_base`；查不到（库已删）回落成 `知识库 {ID}`，不至于空着；
- `fileType`：按 `file_id` 批量反查 `kb_source_file.mime_type` → `FileFormat.ofMimeType(...)` → 枚举名（`PDF` / `DOCX` / …）。
  **不按扩展名猜**：格式的唯一口径是 Tika 魔数识别结果（见 `FileFormat` 注释）。文件校验不通过时**不建来源文件**，所以失败行取不到 MIME → 下发 `null`，界面显示 `—`；
- `failReasonLabel`：`failReason` 是码值，中文名由 `FileValidationFailLabels` 翻译下发 —— 失败原因的种类会随校验规则增加，前端维护映射表必然漂移。

**提交人不下发**：既然只查本人，`kb_user` 反查与 `operator` 字段都一并去掉了（少一次查询、少一列）。

## 涉及的表

| 表                             | 用途                                      |
|--------------------------------|-------------------------------------------|
| `kb_knowledge_base`            | 知识库计数、列表里的库名反查              |
| `kb_pipeline_strategy_version` | 四类可用策略版本计数（`type` + `status`） |
| `kb_file_result`               | 已建档文档数                              |
| `kb_submit_log`                | 「最近提交」的数据源（按 `user_id` 过滤） |
| `kb_source_file`               | 文件类型反查（`file_id` → `mime_type`）   |

两个接口都是纯查询：不写库、不触发任务、不改任何状态。审计动作（`kb_audit_log`）仍由 `AuditEventListener` 写入，只是首页不再读取展示。
