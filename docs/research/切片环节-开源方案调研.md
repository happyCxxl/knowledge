## 一、调研范围

| 序 | 我们的步骤                                 | 要调研的问题                               |
|----|--------------------------------------------|--------------------------------------------|
| 1  | 内容路由（正文 / 表格 / 图片 / 兜底）      | 开源怎么分派与命名算法，兜底是路由还是降级 |
| 2  | 正文聚合（`paragraph-aggregate` 等四算法） | 片长上限怎么设：单参数还是软/硬双参数      |
| 3  | 超长兜底（`recursive-length`）             | 超长文本怎么降级，是否留痕                 |
| 4  | 表格切片（行级 / 行组 / 整表 / 表+引导段） | 表格怎么序列化与重复表头                   |
| 5  | 图片切片（图注占位）                       | 图片片怎么产出，OCR 归谁                   |
| 6  | 后置链（结构重叠 / 碎片合并 / 标题入正文） | 欠长片合并、标题进正文、重叠窗口的通行口径 |
| 7  | 父子层级（父片 + 子片）                    | 层级与自动合并怎么做                       |
| 8  | 编号、token 与对齐键                       | token 估算口径，片序与对齐                 |
| 9  | 统计与观测                                 | 欠长/超长片怎么报                          |

## 二、结论先行

### 2.1 可直接照搬

| # | 做法                                                                                                                                                   | 出处                                                                                                      | 证据等级 |
|---|--------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------|----------|
| 1 | **欠长元素合并成一个"节"直到达到 n 字符**：`combine_under_n_chars`（默认 500）                                                                         | [Unstructured API Parameters](https://unstructured.readthedocs.io/en/main/apis/api_parameters.html)       | 官方文档 |
| 2 | **片长上限用两个参数：软上限 + 硬上限**：`new_after_n_chars`（软，默认 1500）与 `max_characters`（硬，默认 1500）                                      | 同上                                                                                                      | 官方文档 |
| 3 | **分节靠标题，且允许节跨页**：`chunking_strategy=by_title` + `multipage_sections`（默认 true）                                                         | 同上                                                                                                      | 官方文档 |
| 4 | **合并欠长的同级片是默认行为**：Docling `HybridChunker(merge_peers=True)` 默认开                                                                       | [Docling Hybrid chunking](https://docling-project.github.io/docling/_generated/examples/hybrid_chunking/) | 官方文档 |
| 5 | **检索用文本 = 标题路径 + 正文**：Docling 用 `contextualize(chunk)` 产出"上下文增强"文本（输出里 `IBM\n1910s–1950s\n…`），并明确"要嵌的通常是这版文本" | 同上                                                                                                      | 官方文档 |
| 6 | **表格片重复表头**：Docling 有专门的 "Table chunking with header repetition" 一节                                                                      | 同上                                                                                                      | 官方文档 |
| 7 | **切片器与嵌入模型共用同一 tokenizer**：Docling 明确"在 RAG 场景里很重要"，并指出不共用会引发索引错误                                                  | 同上                                                                                                      | 官方文档 |
| 8 | **承认合并后会留欠长的尾巴片**：Docling 明说 "Tail chunks trailing right after merges may still be undersized"                                         | 同上                                                                                                      | 官方文档 |

### 2.2 需改造

| # | 市面做法                                                                                     | 与本项目的差异                                                                             | 改造方向                                                                                                                 | 出处                                                                                                                                                           |
|---|----------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1 | token 计数用真 tokenizer（HuggingFace / tiktoken），并校验"元数据增强后的序列化形态"不超窗口 | 我们用 `tokenDivisor = 1.5`（字符数 ÷ 1.5）估 token，且越界判定按字符数                    | 短期：文档与策略页写明 `tokenCount` 是**估值**（不是模型 token）；中期：把分词的估值口径与「向量化窗口校验」对齐到同一处 | [Docling Hybrid chunking](https://docling-project.github.io/docling/_generated/examples/hybrid_chunking/)                                                      |
| 2 | 软/硬上限是两个独立参数，语义在文档里写得很直白                                              | 我们有 `targetMaxLen`（结算）与 `softMaxLen`（降级阈值），但页面不写范围、也不解释两者关系 | 在策略页与文档里成对说明（本环节已把这两项写进统计键，可直接展示"超目标上限片数 / 超软上限片数"）                        | [Unstructured API Parameters](https://unstructured.readthedocs.io/en/main/apis/api_parameters.html)                                                            |
| 3 | 表格/图片不单独路由，而是"按内容类型走不同元素处理"                                          | 我们有独立四路由 + 算法下拉                                                                | 保留（与我们的策略面更贴合），但把"算法→参数范围"的目录补上，与预处理 `PreprocessParam` 同形                             | 同上                                                                                                                                                           |
| 4 | 结构重叠（`chunk_overlap`）在多数实现里默认开                                                | 我们 `structureOverlap` 默认 0（不重叠）                                                   | 保持默认关（避免检索重复命中），但在文档里写清"要重叠得显式开"                                                           | [LangChain RecursiveCharacterTextSplitter](https://docs.langchain.com/oss/javascript/integrations/splitters/recursive_text_splitter)（仅搜索命中，未展开核对） |

### 2.3 不适用

| # | 做法                                                      | 不适用的原因                                                                                                            |
|---|-----------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------|
| 1 | 语义切片（按 embedding 相似度断点）                       | 依赖嵌入能力且在入库前调用；我们把它保留为预留算法（`semantic` / `semantic-boundary`，`supported=false`），当前阶段不做 |
| 2 | 图片 OCR / 视觉摘要 / 多模态向量成片                      | 我们是"识别归解析、切片只处置产物"的分工：OCR 属解析环节预留（`IMAGE_*` 四个算法均置灰）                                |
| 3 | 多级父子与自动合并（层级解析 + 命中子片自动回溯父片全文） | 我们是**单层父片** + 检索侧 `PARENT_EXPAND` 预留；多级自动合并不做（原 `parentChildDepth` 是本环节的孤儿配置，已删）    |
| 4 | 语料级去重 / 跨文档相似片合并                             | 属切片之后的检索优化，不在本环节职责内                                                                                  |
| 5 | 单一超大分片（不切）                                      | 与"片长要贴合嵌入模型窗口"冲突                                                                                          |

## 三、逐问题对照

### 3.1 正文聚合与片长上限

| 维度       | 市面做法                                                                                            | 出处                                            |
|------------|-----------------------------------------------------------------------------------------------------|-------------------------------------------------|
| 结算条件   | 累计到目标片长即结算；超过软上限停止并入（`new_after_n_chars`），超过硬上限截断（`max_characters`） | Unstructured 官方参数页                         |
| 欠长处理   | 合并到 `combine_under_n_chars`（默认 500）为止                                                      | 同上                                            |
| 边界保留   | Docling 明确"该停在逗号前就停"，不硬切到上限                                                        | Docling 官方示例                                |
| 我们的差异 | 我们有目标上限（800，结算）与软上限（1000，**降级**而不是硬截断），另有碎片合并 300                 | 本环节 `ChunkProperties` 与 `MinMergeProcessor` |

**结论**：口径同源；差异在"硬上限的处理方式"——开源是**截断**，我们是**走兜底降级**（保内容不丢，代价是多出片）。这条差异应在策略页说明，避免使用者以为目标上限是硬约束。

### 3.2 超长兜底

| 维度       | 市面做法                                                                                                | 出处                                                              |
|------------|---------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------|
| 递归切分   | 先按段落、再按句、最后按字符硬切（分隔符优先级列表）                                                    | LangChain `RecursiveCharacterTextSplitter`（未展开核对）          |
| 是否留痕   | 文档层面通常不强调；靠片本身长度观察                                                                    | Docling / Unstructured 文档均未展开                               |
| 我们的差异 | 兜底片标 `contentType=FALLBACK` + `fallbackReason`（"超长段落递归降级" / "标题边界超长降级"），统计单列 | 本环节 `AbstractBodySliceStrategy` / `TitleBoundarySliceStrategy` |

**结论**：我们的留痕比开源细，属于本项目的观测优势（对应审计的 C 类：把降级路径补上用例即可）。

### 3.3 表格切片

| 维度       | 市面做法                                                                                                                  | 出处                                                 |
|------------|---------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------|
| 序列化     | 表格导出为 Markdown / HTML（Docling 有表格导出与"表头重复"章节）                                                          | Docling 官方示例                                     |
| 表头随片   | 明确作为一类能力单列                                                                                                      | 同上                                                 |
| 我们的差异 | 三个表格算法都随片带表头（`headerByCol`），Markdown 管道表；另有"整表一片超限降级行级"与"表 + 引导段落"两种本环节独有形态 | 本环节 `TableMarkdownSupport` / `TableWholeStrategy` |

**结论**：表头随片与开源一致；"表 + 引导段落"是我们针对招投标文档的增强（把表格前的说明段落拼进片），开源未见对等做法，属自述口径，文档里应避免声称"行业惯例"。

### 3.4 图片切片

| 维度       | 市面做法                                                        | 出处                                                                                          |
|------------|-----------------------------------------------------------------|-----------------------------------------------------------------------------------------------|
| 图片成片   | 图注 + 占位文本；OCR 属解析/摄取阶段                            | Unstructured（`extract_image_block_types` 在分区阶段抽图片块）、Docling（导出图片在转换阶段） |
| 我们的差异 | 图注占位为默认且唯一可用算法；OCR / 视觉摘要 / 多模态均置灰预留 | 本环节 `ImageCaptionSliceStrategy` 与 `ChunkAlgorithm` 的 `supported=false`                   |

**结论**：分工与开源一致（识别归上游），无需改造。

### 3.5 后置链（重叠 / 碎片合并 / 标题入正文）

| 维度       | 市面做法                                                                          | 出处                            |
|------------|-----------------------------------------------------------------------------------|---------------------------------|
| 重叠       | `chunk_overlap` 普遍默认开（如 RecursiveCharacterTextSplitter 默认 200 字符级别） | LangChain 文档（未展开核对）    |
| 碎片合并   | 默认开（`combine_under_n_chars=500`；Docling `merge_peers=True`）                 | Unstructured / Docling 官方文档 |
| 标题入正文 | `contextualize()` 产出"标题 + 正文"的检索形态，并明确这是要嵌入的文本             | Docling 官方示例                |
| 我们的差异 | 顺序固定为 结构重叠 → 碎片合并 → 标题入正文（`@Order(1/2/3)`）；结构重叠默认关    | 本环节三个后处理器              |

**结论**：三条能力齐备、顺序合理；两处差异（重叠默认关、合并仅限正文片且不跨表格/图片/章节）都属更保守的取舍，写进文档即可。

### 3.6 父子层级

| 维度       | 市面做法                                                                                                                          | 出处                                                                                                     |
|------------|-----------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------|
| 层级       | 层级节点解析（大节点 + 叶子节点），检索命中叶子后可回溯父节点全文                                                                 | [LlamaIndex 节点解析与 Chunksets（第三方解读）](https://www.poma-ai.com/docs/optimal-chunker-llamaindex) |
| 我们的差异 | 单层父片（每章一条 `SECTION` 片，内容 = 子片拼接）；父片默认不产向量（向量化侧 `includeParent=OFF`），检索侧 `PARENT_EXPAND` 预留 | 本环节 `ChunkPipeline` 父子段                                                                            |

**结论**：单层够用（多级会成倍放大片数）；"父片计入片数却不产向量"这条容易误读，页面已有待定项，文档里要点明。

### 3.7 编号、token 与对齐键

| 维度       | 市面做法                                                                                               | 出处                          |
|------------|--------------------------------------------------------------------------------------------------------|-------------------------------|
| token      | 用真 tokenizer 计数；Docling 建议 chunker 与嵌入模型共用同一 tokenizer                                 | Docling 官方示例              |
| 片序       | 按产出顺序编号；"归档序 vs 阅读序"这一区分开源文档少见                                                 | —                             |
| 我们的差异 | `chunk-0001` 起编号，顺序是"父片全部在前 → 子片 → 孤儿片"（归档序）；`tokenCount = ceil(字符数 ÷ 1.5)` | 本环节 `ChunkPipeline` 编号段 |

**结论**：`tokenCount` 是**字符估算**，与嵌入模型的真实 token 不是一回事——这是 2.2 第 1 条要改造/写明的地方；"归档序不是阅读序"是本项目自述口径，需在文档与页面提示里保留。

### 3.8 参数与配置面

| 维度       | 市面做法                                                                                                                              | 出处          |
|------------|---------------------------------------------------------------------------------------------------------------------------------------|---------------|
| 参数暴露   | 参数集中在一个配置对象上（Unstructured 的 chunking 参数、Docling 的 `HybridChunker` 构造参数），文档逐条给默认值                      | 两份官方文档  |
| 我们的差异 | 参数分两层（路由算法参数 + 流程层键），默认值单一事实源在 `ChunkProperties`，但**保存校验与默认补齐用的是裸字符串**，前端也不显示范围 | 本环节审计 B1 |

**结论**：与 2.2 第 3 条同一件事——补一个与预处理 `PreprocessParam` 同形的"切片参数目录"（键 + 范围 + 默认 + 说明），让后端校验、前端提示、文档三者同源。

### 3.9 统计与观测

| 维度        | 市面做法                                                                                                                           | 出处                                    |
|-------------|------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------|
| 欠长/超长片 | Docling 明确提示"合并后可能有欠长尾巴片"；工具侧一般不做专门统计                                                                   | Docling 官方示例                        |
| 我们的差异  | 统计里有 `overTargetMaxCount` / `overSoftMaxCount` / `fallbackCount` / `orphanCount` / `maxChars` / `avgChars`，但卡片只展示一部分 | 本环节 `ChunkStatsSupport` 与页面待定项 |

**结论**：可参照 Docling 的提醒，在观测里补一项"欠长片数"（低于 `minMergeLen` 且未被合并的片），与已有的超长片数成对。
