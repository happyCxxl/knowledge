# knowledge 项目文档说明

> 统一实施基准（模块架构 + 实施顺序 + 环节操作流程）见根文件 `实施手册.md`。

## 目录组织（2026-08-31 起）

| 目录               | 放什么                                                                                                    | 回答什么问题           |
|--------------------|-----------------------------------------------------------------------------------------------------------|------------------------|
| `steps/`           | 任务文档（阶段实施文档），每阶段一份（step-00、step-01…）：目标与范围、决策、任务清单、验收标准、执行记录 | 这一步做什么、做完没有 |
| `implementations/` | 具体技术实现文档，每个功能一份，与任务文档并列：类/字段/接口/流程/边界/错误处理/测试点                    | 具体怎么写代码         |
| `handover/`        | 环节交接文档（6 份，按两位编号排序）：环节定位/接口/流程/代码地图/表依赖/排查手册                         | 接手某环节先看哪份     |

## 文档流程

1. 每个实施阶段先落任务文档（`steps/step-0X-*.md`）；
2. 涉及功能实现时，**先与用户讨论具体实现方案**——`D:\projects\docs\知识库一期产品交互原型.html` 仅用于评审与边界确认，不规定具体实现细节；
3. 讨论确认后，生成对应的具体技术实现文档到 `implementations/`；
4. 按实现文档写代码、验证，执行结果回填任务文档的执行记录。

> 注意（2026-08-31 决定）：本目录（`docs/`）**已随代码提交 GitLab**；`.gitignore` 仅忽略 `docs/html/`（HTML 产物目录），其余 docs/ 内容正常纳入版本管理。

## 提交约定（2026-09-01 起）

- **代码/文档的 git 提交一律由用户本人执行**，助手不执行 `git commit` / `git push`（曾因助手代提交而整体回退过 step-01 的 5 个提交）。
- 助手完成代码改动后，只汇报改动清单与验证结果，提交命令由用户自行操作。
