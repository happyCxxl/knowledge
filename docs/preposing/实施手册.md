# knowledge 实施手册

> 本文档是项目的统一实施基准：模块架构、总体实施顺序、每阶段的环节操作流程、提交与验证约定。
> 每一步做什么、按什么流程做、怎么验收，以本文档为准；
> 原项目的参考设计档案（step/implementations/handover 文档）保留在 git stash 与 `E:\workbuddy\knowledge-work` 原目录，仅作参考，不在本仓库维护。

## 1. 项目定位

- **单体应用**：后端单进程；前端（knowledge-web）后续配套建设；
- **登录/鉴权自建**：用户、令牌、安全配置均在本项目内实现（不做平台共享能力假设）；
- **无租户概念**：数据模型不含 tenant 语义；
- **不调用外部业务服务**：文件存储、向量库等均为项目自管组件；外部能力仅限开源基础设施（MySQL/Redis/MinIO/Milvus）；
- **按模块拆分，而非分项目**：模块间为工程分层关系，同一构建与部署单元。

## 2. 模块清单与依赖方向

```
knowledge-infra          （零依赖：数据与规范层）
    ↑
knowledge-common         （依赖 infra：领域模型、DTO、枚举、错误码、R 契约、用户模型）
    ↑
knowledge-auth           （依赖 common：登录、用户、令牌、安全配置）
knowledge-file-center     （依赖 common + infra：文件服务模块——上传/下载/档案库 + 内容寻址对象存取，MinIO 提供者可替换）
knowledge-vector         （依赖 infra：Milvus 向量库封装）
    ↑
knowledge-worker         （依赖 common + storage + vector：文档处理引擎）
knowledge-biz            （依赖全部：业务接口层）
```

| 模块                    | 职责                                                                                                                        | 成立时机  |
|-------------------------|-----------------------------------------------------------------------------------------------------------------------------|-----------|
| `knowledge-infra`       | 数据与规范层：五件套基类（BaseInfo/BaseCreateInfo）、雪花主键与 VO Long→String 约定、DbService 模式、Redis 队列组件、通用锁 | 阶段 1    |
| `knowledge-common`      | 领域模型、实体、枚举、错误码、异常、统一返回契约 R、用户模型（KnowledgeUser）与安全上下文工具（SecurityUtils）              | 阶段 2    |
| `knowledge-auth`        | 认证与用户：登录/注册、用户表、JWT、Spring Security 过滤链                                                                  | 阶段 2    |
| `knowledge-file-center` | 文件服务模块：上传/下载、文件档案表（kb_file_object）、内容寻址对象存取；门面 + 存储提供者结构，MinIO 提供者可替换          | 阶段 4    |
| `knowledge-vector`      | 向量库封装：Milvus 客户端生命周期、通用集合管理、查询封装、版本/口径钉版                                                    | 阶段 16   |
| `knowledge-worker`      | 文档处理引擎：输入校验、解析、组装、预处理、切片、向量化、索引                                                              | 阶段 5 起 |
| `knowledge-biz`         | 业务接口层：控制器、服务编排、任务消费、知识库管理、检索评测                                                                | 阶段 3 起 |

## 4. 每阶段统一操作流程（八步）

> 全部阶段（含新建模块的 1/2/4/15）按本流程执行；流程源自原项目环节整理规范的七步工作流（档案存于 stash），扩展了 SQL 迁移一步。

```
① 通读参考档案    从 git stash 取原项目对应档案（step 任务文档 + implementations 实现文档 + handover 交接文档），
                   先理解"做什么、怎么做、验收标准"（档案不在本仓库维护）
② 输出实施清单    助手给出精确清单：模块落位 + 代码文件（含 test）+ 迁移脚本 + 本阶段自实现类的设计要点
③ 逐项确认        用户审阅清单与设计，拍板后开工；有分歧先讨论再动手
④ 执行修改        代码/模块/迁移脚本按清单落地；测试同步（装配变化同步单测，纯映射类用真实实例）
⑤ SQL 迁移        执行本阶段 stage-XX-*.sql 并验证表结构与 seed 落库（表随阶段出现，不提前建全）
⑥ 验证            mvn compile：本阶段清单内文件零错误（后续阶段文件的编译错误属预期，忽略）；
                   能跑的单测即时跑；跑不了的登记到"全量测试"清单（契约补齐后统一执行）
⑦ 暂存与提交      助手 git add 清单 → 用户自查核实 → 用户提交（Conventional Commits）
⑧ 文档随环节提交   本阶段一份实施文档（docs/steps/step-XX-环节名.md：目标/决策/清单/验收/执行记录）与代码同批提交
```

## 6. 提交与验证约定

- **提交由用户执行**；助手负责清单、实现协助与验证，不执行 commit/push；
- **注释规范**：类/方法注释只写"做什么"（职责与行为），不写给谁用、为什么存在、从哪来（大厂规范）；
- **文档表格规范**：Markdown 表格一律按编辑器 Reformat Table 结果书写——内容行 `| 内容 |`（单元格补空格到列宽、两侧单空格），分隔行 `|----|`（无空格，短横线数 = 列宽 + 2，中文/全角按 2 个宽度计）；新增/修改文档后统一执行 `pwsh tools/format-md.ps1`（纯脚本复刻 IDEA 规则，无需启动 IDEA），避免编辑器格式告警；
- 提交信息：Conventional Commits，如 `feat(step-03): ...`、`chore(infra): ...`；
- **SQL 按环节迁移**：迁移脚本以阶段编号命名（`stage-XX-*.sql`），每阶段提交时执行对应脚本（表随阶段出现）；Docker 自动初始化仅对全新环境生效；
- **验收口径**：`mvn compile` 本阶段文件零错误；全部契约补齐后统一跑 `mvn -Prun-tests test`；
- 每阶段结束记录该阶段执行结果（可在对应 step 档案追加执行记录）。
