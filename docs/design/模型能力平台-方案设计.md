# 模型能力平台 · 要做什么、怎么做、技术方案

**一句话**：把「多厂商模型接入」收敛成 `knowledge-model` 的**唯一出口**，让每次模型调用的用量与成本可见（厂商没回 usage 就记 `-1`），并按流量 / 健康 / 预算自动切换模型；配套一个**模型管理页面**维护厂商、密钥、价格、限额与路由策略。

**本文只做设计与取舍，不含实现改动。** 讨论定稿后再按第九节的批次实施。

**阅读顺序**：一（要做什么）→ 二（现状核对）→ 三（目标架构）→ 四（数据模型）→ 五（用量与成本口径）→ 六（路由与流量切换）→ 七（治理与限流）→ 八（管理页面）→ 九（落地路径与验收）→ 十（风险）→ 十一（待决策）→ 十二（变更记录）。

---

## 一、要做什么

### 1.1 目标（G 编号供讨论逐条确认）

| #  | 目标                   | 达成标志                                                                                                                     |
|----|------------------------|------------------------------------------------------------------------------------------------------------------------------|
| G1 | 多厂商、多模型统一接入 | 新增一个厂商只改配置与目录数据，Java 侧只加一个适配器；业务模块不出现任何厂商 SDK 类型                                       |
| G2 | 出口唯一               | 全仓库只有 `ModelGatewayPort` 一条出网调用路径（含解析环节的表格结构 / 版面 / OCR）                                          |
| G3 | 每次调用成本可见       | 每次模型调用在 `kb_model_call_log` 落一行，带 tokens、单价快照、成本、延迟、路由原因；厂商未回 usage 时 tokens 与成本记 `-1` |
| G4 | 按流量自动切换模型     | 依据容量占用（厂商限额，可留空）、健康、延迟三类信号在候选模型间切换，策略可配、可灰度、可回滚、可解释                       |
| G5 | 模型管理页面           | 厂商接入（地址 + 密钥 + 厂商级限额）与模型（能力 / 价格 / 限额 / 优先级）可在页面维护，含连通性测试与用量成本概览            |

### 1.2 明确不做（非目标）

| 不做                             | 说明                                                                                              |
|----------------------------------|---------------------------------------------------------------------------------------------------|
| 不在本仓库部署模型权重与推理服务 | 推理服务在仓库之外，本方案只做接入、治理与计量                                                    |
| 不做提示词工程平台与 RAG 平台    | 只保留接入点，不在此方案内设计                                                                    |
| 不做对外计费结算                 | 只做内部成本可见与告警，不做发票、对账、退款                                                      |
| **不做配额层**                   | 不做租户/团队限流、不做预扣与拦截（已定 D15）；用量只用于**可见与告警**                           |
| **不做日聚合表**                 | 看板与告警直接查明细表（已定 D16），等明细量级上来再评估                                          |
| 不引入独立 AI 网关               | 保留「以后可把厂商级限流与统计下沉到网关」的边界，当前消费方都在本仓库内                          |
| 不做本地 token 估算              | 已确认不引入分词器库；无 usage 即记 **NULL + `usage_unknown = 1`**（口径见第五节）                |
| 不做平台级复杂计量               | 用量分类字典、价格表版本与对账、幂等去重、分档定价、缓存读写拆分、分区与保留期作业一律不做（D20） |

`docs/stages/解析环节/05-待办清单.md` 的 PDF 系列已全部结项；本方案是**新的工作流**（模型平台）。落地批次完成后，再在待办清单新增对应条目并回填提交号。

## 二、现状核对（事实与出处）

| 条目            | 证据                                                                                                                                                                                                                                                                                         | 对本方案的影响                                                                                |

| 框架版本        | 根 `pom.xml`：Spring Boot **3.2.5**、Java 21                                                                                                                                                                                                                                                 | LangChain4j 兼容面宽；若改选 Spring AI 1.0 线要先升 Boot                                      |

| 编排侧现状      | 近期已落地任务状态迁移守卫、下游门禁、优雅停机落终态、产物幂等、任务编排包按角色分层                                                                                                                                                                                                         | 模型调用明细要能挂到**任务/执行**维度（`biz_type` / `biz_id`），便于按任务算成本              |

| 解析侧能力落地  | 三项 provider（`SidecarTableStructureProvider` / `SidecarLayoutProvider` / `SidecarOcrProvider`）+ 三条按信号路由（表格规则失败 / 复杂页 / 整页无文本含图片）                                                                                                                                | 能力语义不变，只换出口与治理                                                                  |

| 能力契约预留物  | `domain/parse/capability` 共 12 个类型：`OcrRequest` 是空壳（注释指向尚不存在的 `ModelGatewayPort.structuredOcr`），`ProviderContext` 为占位；字段完整在用是 `TableRegion`/`TableResult`/`TableCell`、`PageImage`/`LayoutResult`/`LayoutRegion`、`OcrRegion`/`StructuredOcrResult`/`OcrLine` | P0 需定"端口入参用哪一组"，空壳填实或删除（见 3.4）                                           |
| 代码约定        | 判空与异常统一走 `NullUtil` / `ThrowUtil`；环节中文标签收口到枚举                                                                                                                                                                                                                            | P0 落地时按现有工具类与枚举约定写，不新造体系                                                 |

| 运维端点现状    | Actuator 只暴露 `health` 与 `metrics`（`management.endpoints.exposure.include`）；yml 注明 `health` 免认证、**`metrics` 需携带凭证**（以 `SecurityConfig` 为准）                                                                                                                             | 模型指标走 Actuator 时要带凭证；成本看板仍以业务接口 + 明细表为主                             |

## 三、目标架构

### 3.1 分层

```
业务模块（解析 / 问答 / …）
        │  只依赖 Port
        ▼
knowledge-model
  ├─ ModelCatalogPort    能力 × 厂商 × 模型 × 价格 × 限额 × 灰度（DB + 缓存 + 变更事件）
  ├─ ModelRouter         候选过滤 → 排序 → 降级链（route_reason 可解释）
  ├─ ModelGatewayPort    唯一出口：chat / embed / structure / ocr / layout
  └─ 治理装饰器链        凭据 → 并发/排队（可选）→ 缓存 → 超时/重试 → 熔断 → 路由 → 适配器调用 → 计量 → 指标
        │
        ▼
  适配器（LangChain4j 适配器 / 自建 HTTP 契约）
        │
        ▼
厂商 API 与仓库外的推理服务
```

### 3.2 组件职责

| 组件               | 职责                                                                        | 不做什么                                    |
|--------------------|-----------------------------------------------------------------------------|---------------------------------------------|
| `ModelCatalogPort` | 提供可用模型清单、能力匹配、价格、限额、灰度权重、启停状态；变更后可刷新    | 不发起调用                                  |
| `ModelRouter`      | 按策略与实时信号给出有序候选与降级链，写 `route_reason`                     | 不直接调用厂商                              |
| `ModelGatewayPort` | 对外唯一入口，统一请求 / 响应 / `usage` / 错误码                            | 不感知业务语义                              |
| 治理装饰器         | 并发/排队（可选）、缓存、超时、重试、熔断、计量                             | 不做模型选型（选型归 Router）、不做配额拦截 |
| 适配器             | 把统一请求翻译成厂商调用（LangChain4j 或自建契约），回填 `usage` 与模型版本 | 不做记账                                    |
| 计量               | 落 `kb_model_call_log` 明细，并提供按时间范围的查询口径（不做日聚合表）     | 不做实时拦截（本方案无配额层）              |

### 3.3 依赖方向（待决策 D1）

| 选项      | 做法                                                                                                         | 优点                                                 | 代价                                  |
|-----------|--------------------------------------------------------------------------------------------------------------|------------------------------------------------------|---------------------------------------|
| A         | `knowledge-model` 依赖 `knowledge-infra`（直接用 Redis 与令牌桶）                                            | 落地快，治理链与适配器同模块                         | model 变重，infra 与 model 的边界模糊 |
| B（建议） | 治理装饰器放在 `knowledge-infra`（或独立 `knowledge-model-governance`），依赖 `knowledge-model` 的 Port 接口 | 依赖方向干净（infra → model 接口），业务只依赖 model | 多一次装配，需定义治理所需的最小接口  |

### 3.4 与解析环节的衔接

| 解析能力     | 统一出口方法     | 请求契约（现有）                      | 响应契约（现有）                                                     |
|--------------|------------------|---------------------------------------|----------------------------------------------------------------------|
| 表格结构识别 | `structure(...)` | `TableRegion`（页码 + bbox + 文本）   | `TableResult`（行列 + 每格 row/col span + bbox + 置信度 + 模型版本） |
| 版面分析     | `layout(...)`    | `PageImage`（页码 + 尺寸 + DPI）      | `LayoutResult`（区域分类 + 阅读顺序 + 模型版本）                     |
| 结构化 OCR   | `ocr(...)`       | `OcrRegion`（页码 + bbox + imageRef） | `StructuredOcrResult`（逐行文本 + bbox + 置信度 + 模型版本）         |

口径不变的三件事：**只在规则路径判不出结果时才调用能力**、**几何 / 规则口径始终是默认**、**调不通即回落并留痕**。

**契约去重（P0 要一并处理）**：common 的 `domain/parse/capability` 包里有 12 个类型，其中 `OcrRequest` 是**空壳**（注释写着它应是 `ModelGatewayPort.structuredOcr` 的入参，而该端口方法目前并不存在），`ProviderContext` 同为占位；实际在用且字段完整的是上表三组。P0 需明确"端口入参用哪一组"，空壳要么填实、要么删除，避免两套契约并存。

## 四、数据模型

表名沿用 `kb_` 前缀；字段类型按 MySQL 8 约定（时间 `datetime`，金额 `decimal(18,6)`，token `bigint`）。

**定稿口径（D11 / D12 / D13）**：每厂商一把密钥、不按租户区分密钥、不引入代理与多环境不同地址 → **只需两张表**：一张「厂商接入」（密钥与地址的唯一落脚点），一张「模型」；页面上**只有一个入口**（新增模型时就地选或新建厂商），厂商接入不单独占菜单。

### 4.1 `kb_model_vendor`（厂商接入：密钥、地址与厂商级限额的唯一落脚点）

| 字段                                           | 类型                                | 说明                                                        |
|------------------------------------------------|-------------------------------------|-------------------------------------------------------------|
| `id` / `code` / `name`                         | bigint / varchar(64) / varchar(128) | `code` 唯一，如 `dashscope`、`openai`、`zhipu`              |
| `base_url`                                     | varchar(255)                        | **可空**：留空即用适配器内置的官方地址；有代理/多环境时再填 |
| `auth_type`                                    | varchar(32)                         | `BEARER` / `AK_SK` / `CUSTOM`                               |
| `credential_cipher`                            | text                                | 密钥密文（AES-GCM 或 KMS 封装），**接口永不返回明文**       |
| `credential_mask`                              | varchar(64)                         | 展示用掩码，如 `sk-****1234`                                |
| `rpm_limit` / `tpm_limit` / `concurrent_limit` | int                                 | 厂商级限额（一家厂商一行，不做多密钥分摊）                  |
| `status` / `rotate_at`                         | varchar(16) / datetime              | 启停与密钥最后轮换时间                                      |
| `remark`                                       | varchar(255)                        | 备注                                                        |
| 公共字段                                       | —                                   | `created_at` / `updated_at` / `created_by` / `updated_by`   |

唯一键：`code`；索引：`status`。

### 4.2 `kb_model`（模型）

| 字段                                          | 类型                                | 说明                                |
|-----------------------------------------------|-------------------------------------|-------------------------------------|
| `id` / `vendor_code` / `model_key`            | bigint / varchar(64) / varchar(128) | `model_key` 为厂商侧模型名          |
| `display_name`                                | varchar(128)                        | 页面展示名                          |
| `capabilities`                                | varchar(255)                        | 多值，逗号分隔，取值见 4.6          |
| `context_window`                              | int                                 | 上下文窗口（可空）                  |
| `price_in_per_m` / `price_out_per_m`          | decimal(18,6)                       | 每百万 token 单价（可空）           |
| `price_image_per_page` / `price_per_1k_calls` | decimal(18,6)                       | 图像按页、嵌入按千次等非 token 口径 |
| `currency`                                    | varchar(8)                          | `CNY` / `USD`                       |
| `rpm_limit` / `tpm_limit`                     | int                                 | 模型侧限额（与厂商级限额取较紧者）  |
| `priority` / `weight`                         | int                                 | 路由用：优先级与权重                |
| `status` / `effective_from` / `effective_to`  | varchar(16) / datetime / datetime   | 启停与生效区间                      |
| `probe_at` / `probe_result`                   | datetime / varchar(255)             | 最近一次连通性测试结果              |

唯一键：`(vendor_code, model_key)`；索引：`status, capabilities`。

### 4.3 `kb_model_route_policy`（路由策略）

| 字段                                                                    | 类型                              | 说明                                                                                |
|-------------------------------------------------------------------------|-----------------------------------|-------------------------------------------------------------------------------------|
| `id` / `capability`                                                     | bigint / varchar(32)              | 一条策略对应一种能力（`CHAT` / `EMBEDDING` / `OCR` / `TABLE_STRUCTURE` / `LAYOUT`） |
| `tenant_id`                                                             | bigint                            | 空表示默认策略                                                                      |
| `strategy`                                                              | varchar(32)                       | `WEIGHTED` / `PRIORITY` / `COST_FIRST` / `LATENCY_FIRST`                            |
| `fallback_chain`                                                        | varchar(512)                      | 降级顺序（模型 id 列表）                                                            |
| `max_retry` / `cooldown_seconds` / `min_dwell_seconds`                  | int                               | 重试上限、冷却、最小驻留                                                            |
| `capacity_trigger_ratio` / `error_trigger_ratio` / `latency_trigger_ms` | decimal(6,4) / decimal(6,4) / int | 触发切换的阈值                                                                      |
| `shadow_mode`                                                           | tinyint                           | 影子模式开关（只记录本该切到谁，不真切）                                            |
| `version` / `status`                                                    | int / varchar(16)                 | 版本化与启停（支持回滚）                                                            |

### 4.4 `kb_model_call_log`（调用明细，一次模型调用一行）

**口径（已定 D19 / D20）**：只记录**调用费用与基本用量**，够用即止 —— 不搞用量分类字典、不做成本对账流程、不做幂等去重窗口、不做分区分档定价；缺 usage 一律 **NULL + `usage_unknown = 1`**（不写 `-1`、不写 0、不做本地估算）。

| 字段                                                                          | 类型                                             | 说明                                                               |
|-------------------------------------------------------------------------------|--------------------------------------------------|--------------------------------------------------------------------|
| `id` / `trace_id`                                                             | bigint / varchar(64)                             | `trace_id` 关联业务链路                                            |
| `tenant_id` / `biz_type` / `biz_id`                                           | bigint / varchar(32) / varchar(64)               | 业务归属（解析任务 / 问答会话…）                                   |
| `capability` / `vendor` / `model` / `model_version`                           | varchar                                          | 能力与**实际**使用的模型（别名漂移以响应回传为准）                 |
| `prompt_tokens` / `completion_tokens` / `total_tokens`                        | bigint（**可空**）                               | 厂商未回 usage 时为 **NULL**，并置 `usage_unknown = 1`             |
| `usage_unknown`                                                               | tinyint                                          | 1 = 本次用量未知（查询与看板据此算"未知占比"）                     |
| `unit_price_in` / `unit_price_out` / `currency`                               | decimal(18,6) / decimal(18,6) / varchar(8)       | 计价时用的单价（留档即可，一行成本可复算）                         |
| `cost`                                                                        | decimal(18,6)（**可空**）                        | **调用费用**；用量未知或单价缺失时为 NULL                          |
| `latency_ms` / `retry_count` / `fallback_from` / `route_reason` / `cache_hit` | int / int / varchar(128) / varchar(32) / tinyint | 延迟、重试、从哪个模型降级、路由原因、是否命中缓存                 |
| `status` / `error_code`                                                       | varchar(16) / varchar(64)                        | `SUCCESS` / `FAILED` / `TIMEOUT` / `RATE_LIMITED` / `CIRCUIT_OPEN` |
| `created_at`                                                                  | datetime                                         | 调用时间                                                           |

索引：`(tenant_id, created_at)`、`(capability, model, created_at)`、`trace_id`。

> **不做日聚合表（已定 D16）**：看板、成本趋势与告警**直接查本表**（限定时间范围 + 走上面的索引）。
> **不做**（调研建议但按业务需要不采纳，逐条见第十一节「调研结论采纳情况」）：用量分类字典、价格表版本与生效时间、成本对账流程、幂等键与去重窗口、分档定价、缓存读写分别计价、推理/音频单列计价、明细分区与保留期作业。等真实量级或计费诉求出现再评估。
> **一条保留的细节**：流式一律以**结束回执**为准（禁止逐块累加 token）。

### 4.5 枚举字典（口径冻结）

| 字典              | 取值                                                                                                                                                                                 |
|-------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 能力 `capability` | `CHAT` / `EMBEDDING` / `RERANK` / `OCR` / `TABLE_STRUCTURE` / `LAYOUT` / `IMAGE`（可扩展）                                                                                           |
| 状态              | `ENABLED` / `DISABLED`；调用状态 `SUCCESS` / `FAILED` / `TIMEOUT` / `RATE_LIMITED` / `CIRCUIT_OPEN`                                                                                  |
| `route_reason`    | `PRIMARY_OK` / `WEIGHT_PICKED` / `CAPACITY_HEADROOM_LOW` / `ERROR_RATE_HIGH` / `LATENCY_HIGH` / `CIRCUIT_OPEN` / `FALLBACK_FROM` / `SHADOW_ONLY`（无配额层，故无 `BUDGET_EXCEEDED`） |
| `usage_unknown`   | `0` 已知；`1` 未知（tokens 与 cost 记 **NULL**）                                                                                                                                     |
| 未知与零的区别    | `0` 表示确实为零（命中缓存、空响应）；**NULL** 表示**未知**，二者不可混用                                                                                                            |

## 五、用量与成本口径

### 5.1 数据源

| 优先级        | 来源                 | 说明                                                                              |
|---------------|----------------------|-----------------------------------------------------------------------------------|
| 1（唯一权威） | **厂商响应的 usage** | 随调用返回，`inputTokenCount` / `outputTokenCount`（LangChain4j 的 `TokenUsage`） |
| —             | 网关统计             | 不引网关（已定 D13）                                                              |
| —             | 本地估算             | **明确不做**（不引入分词器库；调研显示业界多有估算，我们按业务需要放弃）          |

### 5.2 缺 usage 的处理（已定 D19）

- `prompt_tokens` / `completion_tokens` / `total_tokens` 与 `cost` 全部记 **NULL**，同时置 `usage_unknown = 1`；
- `NULL` 让 `SUM` / `AVG` 天然跳过未知行，不需要在每条查询里写哨兵判断（这是改掉 `-1` 的理由）；
- 页面与接口如实展示「未知占比」，不允许静默按 0 拉低均值；
- 未知占比如异常升高（某厂商改协议、流式不回 usage）要进告警（见 5.6）。

### 5.3 查询口径（直接查明细表）

```sql
-- NULL 行自动被聚合跳过，未知条数单独计数
SELECT SUM(total_tokens) AS tokens_known,
       SUM(cost)         AS cost_known,
       SUM(CASE WHEN usage_unknown = 1 THEN 1 ELSE 0 END) AS unknown_calls,
       COUNT(*)          AS calls
FROM kb_model_call_log
WHERE created_at >= ? AND created_at < ?;
```

查询必须限定时间范围并走 `(tenant_id, created_at)` / `(capability, model, created_at)` 索引。

### 5.4 成本公式

```
cost = prompt_tokens × unit_price_in / 1e6
     + completion_tokens × unit_price_out / 1e6        （token 口径）
cost = image_units × price_image_per_page              （图像 / 版面 / OCR 按页）
cost = calls / 1000 × price_per_1k_calls               （嵌入等按千次）
```

- 单价取自 `kb_model`，**调用时把用到的单价写入明细**（留档，一行成本可复算）；调价不追溯历史；
- 币种随明细存；精度：金额 `decimal(18,6)`，展示 4 位小数；
- **不做**分档定价（长上下文/批次价）与缓存读写分别计价 —— 业务上目前用不到（见第十一节）。

### 5.5 特殊形态的计量规则

| 形态            | 规则                                                                          |
|-----------------|-------------------------------------------------------------------------------|
| 流式            | 以**结束回执**里的 usage 为准；不回 usage → NULL + `usage_unknown = 1`        |
| 工具调用 / 多轮 | **按模型调用计数**，一次业务请求可能落多行（用 `trace_id` + `biz_id` 串起来） |
| 重试            | 每次真实调用各落一行；`retry_count` 递增，`fallback_from` 记录从哪个模型降级  |
| 缓存命中        | 落一行，`cache_hit = 1`，tokens 记 `0`（确实为零），`cost = 0`                |
| 失败调用        | 仍落行；`cost` 按厂商返回的 usage 计算，用量未知则 NULL                       |
| 图像 / 嵌入类   | 按页 / 千次计价，不折算成 token                                               |

### 5.6 告警项（查明细表，只告警不拦截）

| 告警           | 阈值示例                            |
|----------------|-------------------------------------|
| 成本突增       | 日成本环比 ≥ 50% 且绝对值超阈值     |
| 单模型成本异常 | 某模型日成本占总量 ≥ 60% 且环比翻倍 |
| 未知占比       | `usage_unknown = 1` 的比例 ≥ 5%     |
| 厂商限流       | `RATE_LIMITED` 占该厂商调用 ≥ 3%    |
| 路由抖动       | 同一能力 10 分钟内切换 ≥ 5 次       |
| 缓存命中下滑   | 命中率环比下降 ≥ 20%                |

## 六、路由与流量切换

### 6.1 信号与采集点

| 信号     | 采集点                                                          | 说明                                                                                                     |
|----------|-----------------------------------------------------------------|----------------------------------------------------------------------------------------------------------|
| 容量占用 | 治理层的计数（Redis；要主动限速时用已有 Bucket4j）              | 当前 RPM、TPM、并发对比**厂商限额**（`kb_model_vendor` 与 `kb_model`，两处都可留空，留空则不做占用判断） |
| 健康     | LangChain4j `ChatModelListener.onError` + Resilience4j 熔断状态 | 429 / 5xx / 超时 / 解析失败                                                                              |
| 延迟     | `onResponse` 的耗时统计                                         | 近 N 分钟 P95                                                                                            |

无配额层，故**不设"预算/配额"信号**（已定 D15）；成本信号只用于告警与看板，不参与候选过滤。

### 6.2 候选过滤（硬条件，全部满足才入候选）

`status = ENABLED` ∧ 能力匹配 ∧ 所属厂商接入为启用且密钥已配置 ∧ 未熔断 ∧ 不在冷却期 ∧ 在生效区间内。

### 6.3 排序策略（命名与默认值对齐 LiteLLM 的 `routing_strategy`）

| 策略（对齐官方取值）         | 适用           | 排序键                                               |
|------------------------------|----------------|------------------------------------------------------|
| `simple-shuffle`（**默认**） | 生产分流       | 按厂商 `rpm`/`tpm` 余量随机；未配限额则随机          |
| `least-busy`                 | 并发不均时     | 在途请求数升序                                       |
| `usage-based-routing`        | 想均匀贴住限额 | 当前 RPM/TPM 用量最低（官方标注 bad for perf，慎用） |
| `latency-based-routing`      | 交互场景       | 近 N 分钟 P95 升序                                   |
| `cost-based-routing`         | 成本敏感批处理 | 预估成本升序                                         |

**优先级用独立的 `order` 表达**（对齐 LiteLLM）：数值**越小越优先**，同一 `order` 层内再按上面策略挑选；某层全部失败才降到下一层，各层各自重试（FastGPT 的 priority 方向相反，我们采用 LiteLLM 口径）。
口径说明：**默认加权/随机分流**（LiteLLM 官方把 `simple-shuffle` 列为生产推荐默认）；自适应/语义路由不在本期范围（LiteLLM 亦标 BETA）。

### 6.4 降级链

候选全部失败时按 `fallback_chain` 依次尝试；仍失败则回落到**规则路径**（解析环节已有该口径：表格降级为段落、版面按几何顺序、OCR 不补文字）。

### 6.5 防抖与迟滞（避免模型来回跳）

| 机制     | 口径                                                            |
|----------|-----------------------------------------------------------------|
| 阈值窗口 | 指标越线需**持续** `N` 秒（默认 30s）才触发切换                 |
| 最小驻留 | 切换后 `min_dwell_seconds`（默认 120s）内不再切回               |
| 冷却     | 失败模型进冷却 `cooldown_seconds`（默认 60s），冷却期内不进候选 |
| 迟滞带   | 恢复条件比触发条件更严（如触发 80% 占用、恢复到 60% 才切回）    |
| 抖动告警 | 切换频率超阈值即告警（见 5.6）                                  |

### 6.6 粘性粒度

| 场景                      | 粒度       | 理由                                                                                             |
|---------------------------|------------|--------------------------------------------------------------------------------------------------|
| 解析（表格 / 版面 / OCR） | **按页**   | 能力本身是页级的；页与页之间允许换模型，且 `CapabilitySnapshot` 记录每页用了哪个模型版本，可复现 |
| 对话                      | **按会话** | 同一会话中途换模型会影响回答风格与缓存命中；仅以降级形式切换                                     |
| 批处理任务                | 按任务     | 成本归属与失败重跑都按任务维度统计                                                               |

### 6.7 影子模式与灰度

`kb_model_route_policy.shadow_mode = 1` 时只把「本该切到谁」写进 `route_reason = SHADOW_ONLY` 与明细，不真正改变调用；观察一段时间（建议一周）后再打开。

### 6.8 可观测

每次调用写 `route_reason`（见 4.6 字典）、`fallback_from`、`retry_count`；页面提供「按原因统计切换次数」视图。**没有 route_reason 的自适应路由无法排障**，此项为硬要求。

### 6.9 与缓存、一致性的相互影响

- 换模型会降低缓存命中（缓存键含 `model` 与 `model_version`），成本核算要能体现；
- 解析结果质量可能随模型变化，`CapabilitySnapshot` 已记录模型版本，可回溯「同一文档两次解析结果不同」；
- 不允许在同一份文档的同一次解析里对**同一能力**无理由切换模型（除降级外）。

## 七、治理与限流

### 7.1 装饰器顺序（固定顺序，推理与排障都依赖它）

```
凭据解析 → 并发/排队（可选）→ 缓存查询 → 超时/重试
→ 熔断(Resilience4j) → 路由选型 → 适配器调用 → 计量落库 → 指标
```

说明：**本方案没有配额层**（已定 D15），装饰器链里就没有"配额校验"这一步；路由在缓存之后（避免为即将命中的请求做无谓选型），计量在最后且**失败路径同样落库**。

### 7.2 限流：只做"厂商限额感知"，不做配额拦截

| 项                                  | 口径                                                                                                  |
|-------------------------------------|-------------------------------------------------------------------------------------------------------|
| 厂商限额（RPM / TPM / 并发）        | 写在厂商接入与模型两处，**都可留空**；它是**厂商给的上限**，用途是避免把 key 打封并在占用高时触发切换 |
| 触发限流时的行为                    | 收到 429 → 该模型进冷却 + `RATE_LIMITED` 落明细 → 路由按降级链切换；不做主动拦截                      |
| 要不要主动限速                      | 本期不做。若以后需要，复用已有 Bucket4j + Redis（不必新增组件）                                       |
| 配额层（租户/团队限额、预扣、拦截） | **明确不做**                                                                                          |

### 7.3 熔断与重试

- 熔断维度：**模型条目**（对齐 LiteLLM/Kong 的部署维度，不按厂商 —— 同厂商不同模型健康度不同）；半开探测按固定间隔放行少量请求，成功即恢复；
- 可重试：超时、连接失败、429、5xx；**不可重试**：参数错误、内容审核拒绝；
- 退避：指数退避 + 抖动，最大重试次数按能力配置（解析类默认 1，交互类默认 2）；冷却时长可参考厂商 `Retry-After`；
- 组件：熔断引入 Resilience4j（仓库目前只有 Bucket4j 与 Actuator，无同类实现）；**模型指标复用已接入的 Actuator**（`management.endpoints.exposure.include: health,metrics`，只暴露这两个端点；`health` 免认证、**`metrics` 需携带凭证**，以 `SecurityConfig` 为准），不新引一套指标栈。

### 7.4 并发与排队

交互请求与批处理（解析）分队列；解析任务优先级低于交互；队列满时批处理延后重试（不阻塞交互）。

## 十、风险与对策

| 风险                                      | 影响                     | 对策                                                                |
|-------------------------------------------|--------------------------|---------------------------------------------------------------------|
| 框架抽象泄漏（业务依赖 LangChain4j 类型） | 换框架要动业务           | 业务只依赖 `ModelGatewayPort`；用依赖约束 / 架构测试守住            |
| 框架版本快速演进                          | 升级成本                 | 适配器层隔离；固定版本并记录升级评估                                |
| 模型别名漂移（`*-latest`）                | 成本与结果不可追溯       | 以响应回传的模型版本入明细；目录里显式登记版本                      |
| 价格表腐化                                | 成本失真                 | 价格入库 + 生效区间 + 变更审计 + 单价快照                           |
| 路由抖动                                  | 结果不稳定、缓存命中下降 | 阈值窗口 + 最小驻留 + 冷却 + 迟滞 + 抖动告警                        |

### 调研结论采纳情况（调研见 `docs/research/模型能力平台-市面产品调研.md`）

**原则**：调研归调研，方案贴合自身业务 —— 只有能解决我们真实问题的才采纳。

| 调研项                                               | 处置                         | 理由                                                        |
|------------------------------------------------------|------------------------------|-------------------------------------------------------------|
| R1 策略枚举与默认值对齐 LiteLLM                      | **采纳**                     | 命名对齐后团队与外部资料可互通，零成本                      |
| R6 降级链按错误类型分链、429/5xx 切而 400/403 不切   | **采纳**                     | 直接决定降级是否会误伤（参数错误重试无意义）                |
| R7 冷却与熔断按**模型条目**维度                      | **采纳**                     | 修正原设计按厂商维度（同厂商不同模型健康度不同）            |
| R9 冷却时长参考厂商 `Retry-After`                    | **采纳**                     | 一个字段的成本，减少无谓重试                                |
| R12 多副本冷却/用量状态放 Redis                      | **采纳**                     | 已有 Redis，避免各副本各自冷却                              |
| R21 流式以结束回执为准、禁止逐块累加                 | **采纳（只留这一句）**       | DashScope 原生逐块是累积值，累加会重复计费                  |
| R14 `priority` 方向语义写死（小值优先）              | **采纳**                     | 不写死会出事故                                              |
| R28 告警维度（成本/错误率/未知占比/限流/抖动/缓存）  | **部分采纳**                 | 去掉缓存读写 token 告警（我们不做读写拆分）                 |
| R2 用量分类字典（`usage_details`）                   | **不采纳**                   | 我们只有 chat/embedding/图像三类口径，扁平三列够用          |
| R3 `ingested > inferred`（含本地估算）               | **部分采纳**                 | 采纳"只认厂商 usage"；拒绝引入分词器估算（D19）             |
| R4 分档定价 + UI/API 双维护                          | **不采纳（暂）**             | 现用模型无长上下文档位与批次价                              |
| R13 / R19 逻辑模型名与分组                           | **不采纳（暂）**             | 候选集合已由路由策略的 `fallback_chain` 表达，够用          |
| R15 模型级默认请求参数                               | **不采纳（暂）**             | 当前能力调用走固定参数；上 chat 多参数场景再补              |
| R16 模型级超时                                       | **部分采纳**                 | 保留全局超时（已有 `connect/read-timeout`），不做逐模型覆盖 |
| R17 模型级备注/标签                                  | **不采纳（暂）**             | 厂商级 `remark` 够用                                        |
| R18 自动禁用/自动恢复                                | **不采纳（暂）**             | 运行期由冷却与降级处理，模型上下线走页面手动                |
| R22 缓存读写分别计价                                 | **不采纳**                   | 需要按厂商差异维护多套价格键，收益不足                      |
| R23 推理/音频 token 单列                             | **不采纳**                   | 当前能力不涉及                                              |
| R25 价格表版本 + 对账流程                            | **不采纳**                   | 单价随行留档即可复算（D20）                                 |
| R26 明细分区 + 保留期作业                            | **不采纳（暂）**             | 量级未到；真到瓶颈再按调研方案补                            |
| R27 幂等键 + 去重窗口                                | **不采纳（暂）**             | 内部平台不做出账，重复行不影响使用                          |
| R29 零成本可见性指标                                 | **部分采纳**                 | 保留"未知占比"一项（已并入 5.6 告警）                       |
| 独立网关 / 语义路由 / 语义缓存 / 虚拟 key / 会话保持 | **不采纳**                   | 见调研文档第六节"明确不适用"的逐条理由                      |
