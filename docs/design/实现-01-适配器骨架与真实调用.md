# 模型能力平台 · 实现 01：适配器骨架与真实调用

**范围一句话**：把 `knowledge-model` 的平台骨架立起来 —— 契约与端口是我们自己的，模块内部用 LangChain4j（下称 LC4j）的核心模块 `langchain4j-open-ai` 走 OpenAI 兼容协议接入 DashScope，配 `chat` 与 `embed` 两条链路，打一次真实调用跑通（含 `usage` 回填、错误码映射、超时）。

**本篇是逐文件施工口径**：类型与方法签名、配置键、错误码映射、测试用例、手工验收步骤都写到可执行粒度。设计与取舍见 [模型能力平台-方案设计.md](模型能力平台-方案设计.md)。

**边界前提（全文适用）**：契约与端口自有；**业务侧（`knowledge-worker` / `knowledge-biz`）看不到任何 LC4j 类型**；LC4j 只出现在 `knowledge-model` 内部，落在 `engine` 与 `adapter` 两个包。

**入口口径（本片）**：`chat` / `vision` 只传 `vendorCode`；**模型名一处：请求体**（`ChatRequest.modelKey` / `VisionRequest.modelKey` / `EmbeddingRequest.model`）；`embed` 签名本片零改动（见 4.10）。

## 一、范围与不做

### 1.1 归属分工（谁用什么）

| 层                                             | 用什么                                                                                                                                                                                               |
|------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 业务侧（`knowledge-worker` / `knowledge-biz`） | **只用我们自己的契约**：`ChatRequest` / `VisionRequest` / `OutputSpec` / `GenerationResult` / `ModelUsage` 与端口方法；**不出现任何 LC4j 类型**                                                      |
| 平台（`knowledge-model`）                      | 内部用 LC4j：`OpenAiChatModel` / `OpenAiEmbeddingModel`（`baseUrl` 指向 DashScope 兼容端点）、`ChatRequest` / `UserMessage` / `ImageContent` / `ResponseFormat` / `TokenUsage` / `ChatModelListener` |
| 平台对外                                       | 只有我们的契约、`ModelGatewayPort`、`ModelInvoker`、错误码                                                                                                                                           |

附注三条：

1. **同名类只在内部分流**：LC4j 的 `dev.langchain4j.model.chat.request.ChatRequest` 与我们的 `com.knowledge.common.domain.model.ChatRequest` 同名，两者出现在同一个实现文件时用全限定名或局部别名区分；该同名不越过 `knowledge-model` 边界。
2. **架构约束**：`knowledge-model` 之外的模块不得出现 `dev.langchain4j` 开头的 import；该约束由依赖约束与架构测试守住（设计文档风险表「框架抽象泄漏」行）。
3. **换框架只动平台**：`engine` / `adapter` 两个包是 LC4j 的全部落点，替换框架时契约、端口、`ModelInvoker` 与其上层不动。

### 1.2 本片做

| 项           | 内容                                                                                                                                                                                                         |
|--------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 契约与端口   | 平台契约落在 `common/domain/model`；`ModelGatewayPort` 增 `chat` / `vision`（首参 `vendorCode`）；**`embed` 签名保持现状**（见 4.10）                                                                        |

## 三、逐文件清单（平台内部结构）

### 3.1 `knowledge-common` 改动（`com.knowledge.common.domain.model`）

| 文件                                 | 职责                                                                                                                                                                                                    |
|--------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `OutputSpec`                         | 输出约束：`format`（`TEXT` / `JSON_OBJECT` / `JSON_SCHEMA`）+ `schema`（JSON Schema 文本）                                                                                                              |
| `OutputFormat`                       | 同包顶层枚举：`TEXT` / `JSON_OBJECT` / `JSON_SCHEMA`，`OutputSpec.format` 的取值类型                                                                                                                    |
| `AuthType`                           | 鉴权方式枚举，当前只有 `BEARER` 一个取值（D37）                                                                                                                                                         |
| `MessageRole` / `ChatMessage`        | 消息角色与单条消息                                                                                                                                                                                      |
| `ChatRequest`                        | 对话模态入参：`modelKey` + `messages` + `output` + `timeoutMs`                                                                                                                                          |
| `ImageRegion` / `VisionRequest`      | 视觉模态入参：`modelKey` + `imageRef` / `imageBytes` + `region` + `prompt` + `output` + `timeoutMs`                                                                                                     |
| `ModelUsage`                         | 用量：`promptTokens` / `completionTokens` / `totalTokens`，三项都可为 null（D19）；字段与 LC4j `TokenUsage` 对齐为 `Integer`（`inputTokenCount` / `outputTokenCount` / `totalTokenCount`），未知为 null |
| `GenerationResult`                   | `chat` 与 `vision` 共用出参：`content` / `json` / `usage` / `model` / `modelVersion`                                                                                                                    |
| `domain/parse/capability/OcrRequest` | **只改 Javadoc**：预留类型、当前未被使用、平台走 `ModelGatewayPort.vision`；类定义与包名一行不动，**类本身保留**（D28）                                                                                 |

平台不定义字段名、不解释语义：`OutputSpec.schema` 由业务侧写，`GenerationResult.json` 是通用树。

**超时字段的口径**：`ChatRequest.timeoutMs` / `VisionRequest.timeoutMs` 只作契约字段保留 —— **超时只有实例级入口**（builder 的 `timeout(Duration)`，见 4.5 / 5.1），LC4j 1.22.0 的 `ChatRequest` / `ChatRequestParameters` / `ChatRequestOptions` 都没有 per-request 超时入口。

**`usage` 的映射口径**：`ModelUsage` 不是自造的 token 统计，它由 LC4j 回传的 `TokenUsage` 映射而来 —— `promptTokens` ↔ `inputTokenCount`、`completionTokens` ↔ `outputTokenCount`、`totalTokens` ↔ `totalTokenCount`，两者字段类型一致（`Integer`），未知为 null（D19）；映射落在**平台内部**（`knowledge-model` 的 `adapter/OpenAiCompatibleAdapter`），业务侧不出现 LC4j 类型（D40）。

口径四条：

1. **异常只有一种**：自造的异常类已删除，平台不新建异常类，调用失败一律抛 `KnowledgeException`（`knowledge-common` 的统一业务异常），错误码取模型调用分区；**LC4j 异常 → 我们的错误码的映射落在 `invoke/ModelInvoker`（`MODEL-05`）一处**，适配器只把 LC4j 异常原样抛出，LC4j 类型不越过适配器。
2. **"是否可降级"不在错误码里**：`ErrorCode` 只有码值与文案 —— 不加属性、不加重载构造，现有常量零改动。判定归 `MODEL-05` 的调用器：它在把 LC4j 异常映射成错误码时**当场判断**，依据是 LC4j 的 `RetriableException` / `NonRetriableException` 两个基类，另加少量覆盖规则（"输出结构校验失败"、网络类归可降级），逐条见第六节。
3. **detail 带定位信息**：厂商码必带，模型名能取到就带；文案是错误码自身的短语，detail 只补"哪一家、哪个模型"，排障时不必回读配置。
4. **码值分区不交叉**：十个码值连续占 40460~40469，与既有码值不重号；归属模型调用的注释写在该段之上。

**装配口径**：本片只有一个适配器实现，**不建适配器注册表**；`OpenAiCompatibleAdapter` 按仓库习惯用组件注解装配（`@Component` + 构造注入），由 `ModelInvoker` 直接持有；**适配器只持有 `ModelInstanceRegistry`**，不持有 `ModelVendorProperties`，调用时把 `vendorCode` 与请求里的模型名交给注册表取实例。**实例挑选与厂商解析归 `engine/ModelInstanceRegistry`**：未知厂商 → `MODEL_VENDOR_UNKNOWN`（40461），模型名空 → `MODEL_BAD_REQUEST`（40463）。等接入第二种协议时再加"配置里的协议字段 + 按协议选适配器"（届时才需要注册表）。

**请求 / 响应对照（D36 / D39 的落点）**：

| 我们的契约                                                | LC4j 侧                                                                                                                                                                                                                                                                         |
|-----------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `ChatRequest.messages`（`SYSTEM` / `USER` / `ASSISTANT`） | `SystemMessage` / `UserMessage` / `AiMessage` 消息列表                                                                                                                                                                                                                          |
| `ChatRequest.modelKey`                                    | 实例构建时的 `modelName`（实例按模型名缓存，见 4.5）                                                                                                                                                                                                                            |
| `ChatRequest.output` = `TEXT`                             | 不设 `ResponseFormat`；**实测**请求体不含 `response_format`                                                                                                                                                                                                                     |
| `ChatRequest.output` = `JSON_OBJECT`                      | `ResponseFormat.JSON`；**实测**请求体带 `response_format`，取值为 `json_object`                                                                                                                                                                                                 |
| `ChatRequest.output` = `JSON_SCHEMA`                      | `ResponseFormat` + `JsonSchema`（`JsonRawSchema` 传完整自定义 schema，schema 名取 `output`）；**实测**请求体带 `json_schema{name, strict, schema}` 三项，该版本支持 `JsonRawSchema` **直传**，**本片不建提示词注入分支**；缺 schema 在发出请求前抛 `MODEL_BAD_REQUEST`（40463） |
| `ChatRequest.timeoutMs`                                   | **无 LC4j 侧落点**：超时只有实例级入口（builder 的 `timeout(Duration)`，见 4.5 / 5.1）；LC4j 1.22.0 的 `ChatRequest` / `ChatRequestParameters` / `ChatRequestOptions` 都没有 per-request 超时入口，单次覆盖若将来需要，只能另建实例（或等框架支持）                             |
| `VisionRequest.imageBytes` / `imageRef`                   | `UserMessage` + `ImageContent`（本片不实现，第二片接）                                                                                                                                                                                                                          |
| 响应文本                                                  | `ChatResponse.text()` → `GenerationResult.content`；`JSON_*` 输出同时解析进 `GenerationResult.json`                                                                                                                                                                             |
| 响应用量                                                  | 把 `ChatResponse.tokenUsage()`（LC4j 的 `TokenUsage`）转成 `ModelUsage`（三项 `Integer`，缺失留 null，D19）；映射落在 `adapter/OpenAiCompatibleAdapter`                                                                                                                         |
| 响应模型标识 / 版本                                       | `model` 取响应回传值（响应缺失时回填请求模型名）；`modelVersion` 该版本响应不带，留 null                                                                                                                                                                                        |

```java
package com.knowledge.model.engine;
```

口径四条：

1. **职责分层**：工厂**无状态**，只按入参建实例，**不注入** `ModelVendorProperties`，也**不注入** `List<ChatModelListener>`；**厂商解析与未知厂商校验归注册表**（未知厂商 → `MODEL_VENDOR_UNKNOWN` 40461，模型名空 → `MODEL_BAD_REQUEST` 40463）。
2. **key 与构建参数都来自 vendors 配置**（D29 / D38 修订 / D41）：`vendor` 决定 `baseUrl` / `apiKey` / `timeout` / `maxRetries`，`modelKey` 决定 LC4j 的 `modelName`。
3. **懒构建 + 复用**：同 `vendorCode` + 同模型名 + 同模态只建一次实例（`computeIfAbsent` 语义），对话与向量各一张表；实例缓存在进程内，配置变更需重启生效。
4. **类型名与监听器挂载点**：LC4j 1.x 的对话接口是 `dev.langchain4j.model.chat.ChatModel`（0.x 线写作 `ChatLanguageModel`）；**监听器挂载点是工厂构建方法内的 builder**，当前版本未挂，`MODEL-06` 接 `UsageRecordingListener` 时挂上（两个构建方法的注释里已写明挂载点）。

**重试与超时口径（D38 修订 / D41，含实测）**：`timeout-ms` 映射 LC4j 的 `timeout`（**单一总超时**，不区分连接与读取，**实例级唯一入口**）；`max-retries` 映射 LC4j 的 `maxRetries` —— **LC4j 的重试开着，平台不另加重试**。实测三条：`maxRetries=0` 时失败只发 **1** 次请求；`maxRetries=2` 时发 **3** 次请求；`timeout` 取 300 毫秒能切断 1500 毫秒的慢应答并抛 `dev.langchain4j.exception.TimeoutException`。换模型降级与冷却归目录 / 路由片。

| 调适配器、回填 `usage` 与模型版本                                                                                                                                          | 不做冷却、在途计数、延迟 EWMA                       |
| 错误映射与分类：**把 LC4j 异常映射成我们的错误码**，并在同一环节按 `RetriableException` / `NonRetriableException` 当场判断**是否可降级**（见第六节），供后续片的降级链取用 | 不落计量、不做指标；不做缓存、不做排队              |

**重试与退避口径**：同一实例内的重试与退避**由 LC4j 承担**（`max-retries` → `maxRetries`，见 5.1），`ModelInvoker` **不另加重试**；错误分类的用途是**决定是否可降级**，判定在映射 LC4j 异常时当场完成 —— 判据是那两个基类，另加少量覆盖规则（见第六节）：可降级 = 限流 / 请求超时 / 服务端错误 / 网络不可达（含 DNS 解析失败与连接被拒）/ 输出结构校验失败，不可降级 = 未支持模态、厂商未配置、鉴权失败、参数或内容被拒、模型不存在；降级链归目录 / 路由片（见第十节）。

```java
    @Override
    public void onResponse(ChatModelResponseContext context) { ... }

    @Override
    public void onError(ChatModelErrorContext context) { ... }
}
```

口径：`GenerationResult.usage` 由适配器从 `ChatResponse.tokenUsage()` 直接取（同步路径最稳），监听器与它共用同一份 `TokenUsage`，负责延迟、错误与**尝试次数**的记录、并按日志级别打印一行；`retry_count` **按 `onRequest` 触发次数推算**（每次尝试回调一次，尝试次数 − 1）。本片**只回填与打日志**，明细落库归计量片。LC4j 的回调方法名与上下文类型名（`onRequest` / `onResponse` / `onError` 与 `ChatModelRequestContext` / `ChatModelResponseContext` / `ChatModelErrorContext`）以实现时该版本 Javadoc 为准。

### 5.2 启动期校验（D35 / D37）

| 校验项                                                       | 不满足时的行为                                                                      |
|--------------------------------------------------------------|-------------------------------------------------------------------------------------|
| `vendorCode`（Map 键）非空                                   | 启动失败，消息里指出该厂商码                                                        |
| `auth-type` ∈ 该厂商归属适配器的 `supportedAuthTypes()`      | 启动失败，消息里指出该厂商码与其 `auth-type`                                        |
| `api-key` 解析不出来（空 / 未设置）                          | 启动失败，消息里指出该厂商码                                                        |
| `base-url` 给了就必须是合法 URL（http/https）                | 启动失败，消息里指出该厂商码                                                        |
| `auth-type` 落在唯一适配器 `supportedAuthTypes()` 的支持集内 | 启动失败，消息里指出该厂商码与其 `auth-type`（适配器名与 `auth-type` 一起写进消息） |

口径四条：

1. **只校验配置里列出的厂商**：`knowledge.model.vendors` 没列的厂商不进校验，也不进运行时；
2. **缺密钥即失败**：`api-key` 解析不出来（空 / 未设置）直接终止启动，错误信息里带**厂商码**；不做"记警告继续跑"；
3. **占位符写 `${ENV_VAR:}`（带空默认）**：环境变量没设时绑定到空串，由校验器给出"该厂商码缺 api-key"的可读错误，不由 Spring 抛"占位符无法解析"；
4. **不做适配器覆盖校验**：本片只有一个适配器实现、直接注入，配置里没有协议字段，启动期不校验"厂商码能被哪个适配器覆盖"（接入第二种协议时再加这条）。

校验落在 `ModelVendorProperties` 的 `@PostConstruct`，首个不通过即抛异常终止启动。

## 六、错误码映射与结构校验

**落点**：**LC4j 异常 → 我们的错误码的映射落在 `invoke/ModelInvoker`（`MODEL-05`）**；适配器层保持"原样抛出 LC4j 异常"，不自行转换。下表第 2、4 列是 LC4j 侧事实，第 5 列是调用器的可降级判定归属。

| 触发条件                                          | LC4j 侧类名（包 `dev.langchain4j.exception`） | 我们的错误码                          | LC4j 是否内部重试（由两个基类决定） | 可降级判定归属（`MODEL-05` 调用器）  |
|---------------------------------------------------|-----------------------------------------------|---------------------------------------|-------------------------------------|--------------------------------------|
| 未配置该厂商（注册表拒绝，见 4.5）                | —                                             | `MODEL_VENDOR_UNKNOWN`（40461）       | —                                   | 平台侧规则：不可降级                 |
| 模型名为空（注册表拒绝，见 4.5）                  | —                                             | `MODEL_BAD_REQUEST`（40463）          | —                                   | 平台侧规则：不可降级                 |
| `JSON_SCHEMA` 缺 schema（适配器翻译时拒绝）       | —                                             | `MODEL_BAD_REQUEST`（40463）          | —                                   | 平台侧规则：不可降级                 |
| 适配器未实现该模态（本片的 `vision`）             | —                                             | `MODEL_MODALITY_UNSUPPORTED`（40460） | —                                   | 平台侧规则：不可降级                 |
| 密钥无效 / 无权限（HTTP 401 / 403）               | `AuthenticationException`                     | `MODEL_AUTH_FAILED`（40462）          | 否（`NonRetriableException` 子类）  | 基类判定：不可降级                   |
| 触发限流（HTTP 429）                              | `RateLimitException`                          | `MODEL_RATE_LIMITED`（40465）         | 是（`RetriableException` 子类）     | 基类判定：可降级                     |
| 参数错误（4xx；不含 401 / 403 / 404 / 408 / 429） | `InvalidRequestException`                     | `MODEL_BAD_REQUEST`（40463）          | 否（`NonRetriableException` 子类）  | 基类判定：不可降级                   |
| 内容审核拒绝                                      | `ContentFilteredException`                    | `MODEL_BAD_REQUEST`（40463）          | 否（`NonRetriableException` 子类）  | 基类判定：不可降级                   |
| 模型不存在（HTTP 404）                            | `ModelNotFoundException`                      | `MODEL_NOT_FOUND`（40464）            | 否（`NonRetriableException` 子类）  | 基类判定：不可降级                   |
| 服务端错误（HTTP 5xx）                            | `InternalServerException`                     | `MODEL_SERVER_ERROR`（40467）         | 是（`RetriableException` 子类）     | 基类判定：可降级                     |
| 响应体不是合法 JSON                               | `JsonReadException` / `JsonException`         | `MODEL_SERVER_ERROR`（40467）         | 否                                  | 覆盖规则：可降级                     |
| 结构不符预期（响应缺 `choices` 等）               | 同上的 JSON 读异常                            | `MODEL_SERVER_ERROR`（40467）         | 否                                  | 覆盖规则：可降级                     |
| 超时（HTTP 408 或客户端读 / 连接超时）            | `TimeoutException`                            | `MODEL_TIMEOUT`（40466）              | 是（`RetriableException` 子类）     | 基类判定：可降级                     |
| DNS 解析失败                                      | `UnresolvedModelServerException`              | `MODEL_UNREACHABLE`（40468）          | 否                                  | 覆盖规则：可降级                     |
| 连接被拒                                          | `TimeoutException`                            | `MODEL_UNREACHABLE`（40468）          | 是（`RetriableException` 子类）     | 基类判定：可降级                     |
| 输出未过结构校验                                  | —（平台侧校验，LC4j 不感知）                  | `MODEL_OUTPUT_INVALID`（40469）       | 否                                  | 覆盖规则：可降级（可作降级触发条件） |

口径五条：

1. **映射集中一处**：LC4j 的异常 → 我们的错误码落在 `invoke/ModelInvoker`（`MODEL-05`）；适配器把 LC4j 异常原样抛出，不自行转换，LC4j 类型只出现在 `engine` / `adapter` 两个包。映射只产出"码 + detail"，不带任何调用策略。
2. **可降级判定集中一处、且不落在错误码上**：`ErrorCode` 只是一张码值 + 文案的表，不带任何调用策略 —— 没有布尔属性，也没有为它加重载构造。判定归 `invoke/ModelInvoker`（`MODEL-05`）：它在映射 LC4j 的同一个环节当场判断，判据是 LC4j 的 `RetriableException` / `NonRetriableException` 两个基类（表第 4 列是 LC4j 自身的行为，平台不另加重试），另加两条覆盖规则 —— 响应不可解析（JSON 读异常）与平台侧结构校验失败归可降级，网络不可达（DNS 解析失败、连接被拒）归可降级。判定结果是调用器内部的分类结果，供后续片的降级链取用。
3. **LC4j 异常类名与包名已核实并钉进本表**：包 `dev.langchain4j.exception`，第 2 列即确定类名；第 4 列由 `RetriableException` / `NonRetriableException` 两个基类决定，**`maxRetries` 的重试口径据此分类，平台不维护白名单**。**回调方法名与上下文类名（4.8）仍按该版本 Javadoc 核对**，实施首步一并回填。**404（模型不存在）归 `MODEL_NOT_FOUND`（40464）**，与参数错、内容被拒区分开。
4. **`usage` 回填**：响应带 `TokenUsage` → 三项数值按 `Integer` 填入 `ModelUsage`；响应不带 → `ModelUsage` 三项留 null（D19）。`model` 取响应回传值（响应缺失时回填请求模型名），`modelVersion` 该版本响应不带、留 null。
5. **重试与超时的实测记录（本片）**：`maxRetries=0` → 失败只发 **1** 次请求；`maxRetries=2` → **3** 次请求；`timeout` 取 300 毫秒 → 1500 毫秒的慢应答被切断并抛 `dev.langchain4j.exception.TimeoutException`（与本表第 2 列的超时类一致）。**超时只有实例级入口**：LC4j 1.22.0 的 `ChatRequest` / `ChatRequestParameters` / `ChatRequestOptions` 都没有 per-request 超时入口（逐个核对类成员所得），请求体里的 `timeoutMs` 当前不落到 LC4j。

### 6.1 结构校验口径（D39）

| 环节              | 归属                                                                    | 口径                                                                                                                                                                                                                 |
|-------------------|-------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `OutputSpec` 翻译 | `adapter/OpenAiCompatibleAdapter`                                       | 实测**直传成立**：`TEXT` 不带 `response_format`，`JSON_OBJECT` 带 `json_object`，`JSON_SCHEMA` 带 `json_schema{name, strict, schema}`（`JsonRawSchema` 传完整自定义 schema）；**不建提示词注入分支**；厂商差异不外溢 |
| 结构校验          | `validate/OutputSchemaValidator`，由 `invoke/ModelInvoker` **一处**触发 | `TEXT` 不校验；`JSON_OBJECT` 只校"是否合法 JSON"；`JSON_SCHEMA` 用 `com.networknt:json-schema-validator` 做**严格 schema 校验**（"是否满足 schema"）；**默认开启**；适配器不复做                                     |
| 校验失败          | 视为失败                                                                | **不重试**（平台侧校验，LC4j 不感知），抛「输出结构校验失败」错误码（40469）；按第六节的覆盖规则归可降级，**可作降级到下一个模型的触发条件**，降级链归后续片                                                         |

三类输出：`TEXT` 不做结构校验；`JSON_OBJECT` 只校"是否合法 JSON"；`JSON_SCHEMA` 用 `com.networknt:json-schema-validator` 做**严格 JSON Schema 校验**（依赖版本由根 pom 的属性单点钉定，实测解析为 3.0.8，见 2.1 / 2.2）。`JSON_SCHEMA` 的 `schema` 为空时在发出请求前失败，抛 `MODEL_BAD_REQUEST`（40463），消息里指出缺 schema。校验失败抛「输出结构校验失败」错误码、**不重试**、可作降级触发条件。

## 八、验收步骤

1. `mvn -o verify` 通过（含 checkstyle / PMD / CPD / SpotBugs）。
2. `node tools/check-comments.mjs` 与 `node tools/check-encoding.mjs` 通过。
3. **错误码面核验**：`knowledge-model/.../gateway/` 下只剩 `ModelGatewayPort`，没有自造异常类；十个模型调用码值在 `ErrorCode` 内，只有码值与文案，单测逐个断言通过。
4. **`embed` 签名零改动核验**：`EmbedPipeline`（worker）与 `SearchServiceImpl`（biz）及其两处测试逐行无 diff（`git diff --stat` 对这几个文件为空）；`DashScopeEmbeddingProvider` 改造后对同一批文本的向量结果行为不变（维度、顺序、`requestId` 回填）。
5. 在部署环境变量里配真 `DASHSCOPE_API_KEY`，跑 smoke 用例，贴出真实 `content` 与 `usage`。
6. 把 `api-key` 配成一个无效值启一次，确认启动失败且消息里指出是 `dashscope`。
7. 调 `vision(...)`，确认得到「模型未支持该模态」错误码（40460，本片无视觉实现）。
8. 架构约束核验：`knowledge-model` 之外的模块 grep 不到 `dev.langchain4j` 引用（或由架构测试断言）。
9. 依赖面核验：`mvn -o dependency:tree` 里没有 `langchain4j-community-*`，只有 `langchain4j-open-ai`、`langchain4j-core` 与 `com.networknt:json-schema-validator`（版本与根 `pom.xml` 的属性一致）。
10. 适配器面核验：`adapter` 包里只有一个实现类，`ModelAdapter` 上 grep 不到 `vendorCode` / `protocol` 方法，也没有 `AdapterRegistry`。
11. `embed` 厂商解析核验：配两个兼容厂商时启动失败，消息提示"embed 需要指定厂商，等目录片支持"。

## 九、风险与回退

| 风险                                                                                                       | 影响                             | 对策                                                                                                                                             |
|------------------------------------------------------------------------------------------------------------|----------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------|
| LC4j 版本与 API 漂移（`ChatModel` 与旧线的 `ChatLanguageModel`、异常类名、`timeout` 与 `maxRetries` 语义） | 升级要动 `engine` / `adapter`    | LC4j 只落在两个包；版本由根 pom 单点钉；实施首步按 Javadoc 核对类名与方法名                                                                      |
| 误引 community 模块                                                                                        | 依赖面膨胀、接入路线分叉         | 依赖清单只列 `langchain4j-open-ai`；验收用 `dependency:tree` 核一遍（第八节第 8 条）                                                             |
| DashScope 兼容端点与 OpenAI 官方参数差异（`response_format`、图片入参）                                    | 结构化输出与图片通路走不通       | `response_format` 三条已实测直传成立（`JSON_SCHEMA` 走 `JsonRawSchema`，见 4.4 / 6.1）；图片通路第二片接前先打一次真调用验证                     |
| Jackson 版本被 Boot 的 `dependencyManagement` 压低（LC4j 声明 2.22.1，实测解析 2.15.4）                    | 升级或换 Boot 版本时出现链接错误 | **实测未复现冲突，不另钉 Jackson 版本**；`probe/JacksonCompatibilityProbeTest` 保留为常驻兼容性用例（含 `response_format` 与向量路径，见 2.2）   |
| `json-schema-validator` 版本与既有依赖管理口径不符                                                         | 版本漂移或与 Boot 3.2.5 冲突     | 版本由根 `pom.xml` 的属性单点钉定（不写死）；本仓库实测解析 **3.0.8**，其传递的 `tools.jackson.*` 与 `com.fasterxml` 2.x 并存不冲突（2.1 / 2.2） |
| 真实调用的费用与配额                                                                                       | smoke 消耗额度                   | 用例只在环境变量存在时执行；输入取最短；不进 CI 默认链路                                                                                         |
| `api-key` 缺失导致启动失败                                                                                 | 配了该厂商的环境起不来           | **只校验配置里列出的厂商**：不配 `knowledge.model.vendors` 即可启动；错误消息点名厂商码与配置键（D35）                                           |
| `embed` 的厂商解析限制（规则 A）                                                                           | 配了多个兼容厂商时嵌入链路起不来 | 兼容厂商只有一个即直用；多个则启动失败并提示"embed 需要指定厂商，等目录片支持"；签名与参数统一归目录片（4.10）                                   |
| 本地假服务与真实协议的偏差                                                                                 | 映射分支漏测                     | 假服务按 OpenAI 兼容响应结构构造；smoke 打真实端点复核一遍                                                                                       |

**实施前需核实的结论（MODEL-01 已核实并写回）**：

| # | 核实项                                        | 结论                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
|---|-----------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1 | `<langchain4j.version>` 与 Java / Boot 兼容   | `langchain4j-bom` 的当前稳定 release 取 **1.22.0**（官网 Javadoc 的构建号为 1.23.0-beta33-SNAPSHOT，属 beta 线，不取）；LC4j 1.x 要求 **Java 17+**，本仓库 Java 21 满足；**不用** LC4j 的 Spring 集成，与 Boot 3.2.5 无约束关系。实施首步复核一次 Maven Central 元数据（2.1）                                                                                                                                                                                                                                                                                                 |
| 2 | builder 落点（`OpenAiChatModel.builder()`）   | `baseUrl(String)` / `apiKey(String)` / `modelName(String)`；**`timeout(Duration)`** —— 单一总超时，不区分连接与读取，与 D41 一致；**`maxRetries(Integer)`** —— Javadoc 未标注默认值，**实施时按代码或实测确认，文档口径保持"留空用 LC4j 默认"**；`listeners(List<ChatModelListener>)` 与 `listeners(ChatModelListener...)`；`logRequests(Boolean)` / `logResponses(Boolean)`；`useInputImageFormat(Boolean)`（默认走 OpenAI Chat Completions 的 `image_url` 格式）；另有 `customHeaders(Map)` 与 `customHeaders(Supplier<Map>)`（每次请求前取一次，可放动态凭证 —— 记录备查） |
| 3 | LC4j 异常类名与包名                           | 包 **`dev.langchain4j.exception`**，类名与触发条件见第 6 节映射表；**两个基类 `RetriableException`（瞬时错误）与 `NonRetriableException`（永久错误）**，LC4j 的 `maxRetries` 据此分类决定重试，平台**不维护**"哪些异常该重试"的白名单                                                                                                                                                                                                                                                                                                                                         |
| 4 | `json-schema-validator` 的版本                | Maven 上并行存在 **1.5.x**（如 1.5.8）与 **3.x** 两条线；本仓库已取 **3.0.8**（`mvn -o dependency:tree` 实测解析版本），由根 `pom.xml` 属性单点钉定（2.1 / 2.2）                                                                                                                                                                                                                                                                                                                                                                                                              |
| 5 | `ChatModelListener` 回调方法名与上下文类名    | 以实现时该版本 Javadoc 为准；实施首步核对（4.8）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| 6 | `DashScopeEmbeddingProvider` 改造后的行为核验 | 4.10 已定 ①；验收第 3 条逐行核验无 diff，并对同一批文本的向量行为做一致性核验                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

**回退方式**：撤 `langchain4j-open-ai` 与 `json-schema-validator` 依赖及 `engine` / `adapter` 新增类；同时恢复 `DashScopeProperties` 与 `DashScopeEmbeddingProvider` 原实现；业务侧不感知，`EmbedPipeline` / `SearchServiceImpl` 无需回退。
